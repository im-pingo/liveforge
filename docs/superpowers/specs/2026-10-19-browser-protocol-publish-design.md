# Browser camera and microphone publishing through SIP and GB28181

The user wants `/console/publish` SIP and GB28181 modes to capture the actual browser camera and microphone, with the same device selection and preview as WHIP. The current page starts generated protocol-lab media instead. This change extends the existing transports and session lifecycle; the authorized outcome includes implementation and verification in the current working tree.

Browser capture uses a temporary WHIP stream with strictly negotiated H.264 and the protocol's G.711 codec (SIP PCMA/PCMU, GB28181 PCMA). Browser capability failure is explicit before creating a protocol session. The server's existing lab publish request accepts optional `source_stream_key`, reads that stream's captured publisher generation, and sends its actual frames into the normal loopback SIP RTP or GB28181 PS/RTP ingress. Omission preserves the existing deterministic lab API. The publish page always uses the camera path; existing receive/test tools remain on their management pages.

Source and target keys must be distinct valid stream keys. Source startup/codec/subscribe admission must succeed before signaling. The media reader must respect bounded snapshots, ring overwrite, publisher replacement and cancellation; it must not manufacture media or attach to a replacement generation. No new transcoder dependency, public listener, or arbitrary external destination is introduced.

UI state owns one run generation, capture PeerConnection, temporary WHIP resource and protocol session. Stop, page exit, protocol switch and failed setup release owned resources. Late setup responses are cleaned up without affecting a newer run. An active browser capture alone is not proof that protocol publishing succeeded; the page waits for protocol session creation and observes terminal state. Local preview and outbound statistics remain available in all modes.

Verification requires source-content regressions through both real protocol ingress paths, codec/missing-source rejection, replacement/stop cleanup, and browser fake-device capture with H.264/G.711 negotiation and increasing audio/video counters on the target. Fake browser devices test the same getUserMedia path without recording the user's surroundings. Documentation must distinguish this from the deterministic lab workflow and record any native/browser environment blocker.
