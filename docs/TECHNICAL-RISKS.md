## 2026-10-19 Input Boundary and Receive Pipeline Fixes

This round rechecked the actual source code and receive paths. The fixes below address reproduced issues; a historical entry marked "Closed" refers only to its corresponding regression coverage and does not mean every input and deployment combination has passed a security audit.

- **High priority: RTSP control messages could allow unbounded reads or occupy connections for long periods.** The server and cluster peers share a bounded reader: 8 KiB per line, 64 KiB of total headers, and a 1 MiB body; duplicate/invalid Content-Length and Transfer-Encoding are rejected before body allocation. The server waits at most 60 seconds for the next byte and allows at most 10 seconds to complete the packet once it starts; a real TCP incomplete-body regression checks that the connection slot is released.
- **High priority: Malicious H.264 aggregation and fragmentation lacked complete input protection.** Reproduction confirmed a panic caused by a single trailing length byte in STAP, as well as acceptance of orphaned, out-of-order, and cross-source FUs. Format and continuity are now validated before bounded assembly; NAL/FU is limited to 16 MiB, FU to 16384 fragments, and SPS/PPS to 65535 bytes each, with fragments released on errors. This protection validates encapsulation and resource boundaries; it does not claim complete H.264 syntax validation.
- **High priority: Upper-layer frame assembly bypassed the NAL limit, and packet loss could stop reception.** Previously, RTSP accumulated 19,656,000 bytes after 14000 ordinary NALs without a frame ending; losing one FU packet terminated the UDP worker while the publisher/session remained online. RTSP/WHIP now share complete-frame limits (16 MiB+4 bytes, 16384 packets), discard damaged frames, and recover on a subsequent new frame; publisher closure/replacement remains a termination condition. WHIP no longer appends data left over from before an error to subsequent frames.
- **High priority: RTSP tracks shared frame assembly state and clocks.** Parsing is serialized, with frame assembly and time bases isolated by payload type; audio uses its own RTP clock rate and immediately emits complete samples. Regressions cover interleaved tracks, concurrent input, 20 ms Opus time steps, and publisher replacement during parsing. Parsing and lifecycle locks are separate to avoid blocking closure; no cross-track synchronization based on RTCP sender reports was added.
- **Medium priority: Notification WebSockets still accepted connections after closure, and browser origin validation was disabled.** Close permanently closes admission; subsequent handshakes return 503, and connections being upgraded are closed before registration. The library's default Origin host/port validation is restored (scheme is not compared); native clients without an Origin remain usable, and management authentication and server:read permission remain enforced.
- **Verification reliability: RTMP/HLS and file permission tests contained unstable assumptions.** Real-time publishing avoids submillisecond timing and HLS segment eviction far ahead of playback speed; HLS waits for actual GOP/audio readiness; intentionally insecure audit files are explicitly set to 0644 to avoid interference from the process umask. Existing frame-count, playback, and security-rejection assertions are retained.

See [Protocol Input Safety](recipes/protocol-input-safety.md) for limitations, compatibility, and revalidation entry points. Verification results after the final code freeze:

- The new portable server and Loop executor builds passed; the full-repository portable tests using this server through `LF_BINARY` passed: 56 tested packages, 2990 tests/subtests, no failures or skipped tests, plus 1 command package without tests. Coverage includes the origin-edge subprocess and portable Console browser tests.
- The final race checks for all four complete RTSP, WebRTC, notify, and RTP packages passed; full-repository portable `go vet`, documentation self-tests, documentation diff checks, and whitespace checks passed.
- Records of the first two failed full-repository runs are retained locally; they identified fragments retained by the old depacketizer, WHIP fixture timestamps, and AV1 retained-capacity issues. Reruns after the fixes produced the final passing result. See the [Fix and Verification Record](superpowers/plans/2026-10-19-project-hardening.md) for details.
- The local Xcode license has not been accepted, so the final server build with `audiocodec` still fails in `runtime/cgo`; the full FFmpeg/tagged race/coverage baseline and native browser soak gate remain incomplete. `check-review-regressions.sh` stopped at cluster compilation for the same reason after the documentation and core race steps. Further decomposition of large receive modules should follow existing protocol/lifecycle boundaries and preserve testable behavior, avoiding a wholesale rewrite.

## Historical Focused Regressions (2026-09-09)

### 2026-09-09 FFmpeg RTMP Playback Regression

- **Additional reproduction of the user's long GOP**: The actual command used 30 fps, libx264 `veryfast`, and `zerolatency`, with no `-g`; ffprobe confirmed High Profile and no B-frames, with an actual GOP of 8.33 seconds. High Profile itself has not been confirmed as the root cause of this decoding failure, and an independent browser can decode this input. The 300-frame mixed GOP cache covered only about 3.9 seconds; the old snapshot connected the truncated prefix directly to LiveCursor, omitting the reference frames in between. The complete startup chain is now recovered from the ring buffer when it still retains a keyframe; if the keyframe has been overwritten, it explicitly waits for the next keyframe without bridging missing data. Temporary replay references at most one ring's worth of frames, and the persistent cache limit is unchanged.
- **HLS startup**: The original video's autoplay bypassed the 0.15-second readiness threshold, and using the end of the last buffered range incorrectly counted data across gaps as playable buffer. The hls.js path now disables autoplay, waits for 0.8 seconds of continuous buffer at the current playback position, and sets the target live latency to 1.5 seconds. The new browser regression produced `Autoplay=true, EarlyPlays=1` on the original implementation; after the fix, playback starts once, only when continuous buffer is ready.
- **Long-GOP fix verification**: Portable and tagged builds, focused snapshot/GOP race checks, the full core race checks, Console buffering regressions, lint, documentation checks, and the full tagged race/coverage suite passed. The concurrent ingress fixture now explicitly asserts that a broken prefix is not replayed when its keyframe has been overwritten and that a complete snapshot is restored after a new keyframe. An independent `18091` instance replicated the same user stream through RTMP; its default WebRTC preview reached 640x360, `readyState=4`, and `currentTime=0.363` within about one second of opening, then continued advancing. HLS initially paused to wait for buffering, then played normally; it continued advancing after repeated startup, with no browser warning/error. That instance was retained for acceptance testing; the active publisher on the original `8090` was neither restarted nor kicked, and the switchover time remained for the user to choose. Explicit WebRTC-Realtime still waits for the next keyframe, with a worst-case wait approaching 8.33 seconds for the current input.

- **Initial reproduction scope**: The user's `127.0.0.1:8090` instance at that time was a portable build reporting `audio_transcoding=false`. With continuous FFmpeg H.264+AAC publishing, Console WebRTC returned `WHEP 415: source audio codec is not supported by the offer`. The initial HLS/DASH checks covered only synthetic input with a two-second GOP; the original command was later confirmed from the running FFmpeg process. See above for the subsequent long-GOP issues and fixes.
- **Root cause and fix**: Console's unconditional audio-track request conflicted with WHEP's strict validation of requested tracks. When AAC/MP3 is known and the server explicitly lacks transcoding capability, mixed streams request video only and persistently display "Video only"; audio-only streams display a capability error. Negotiation is retained when capability information or the codec is unknown. Feeds without a requested audio track no longer create invalid transcoding jobs with an Unknown target; external requests for incompatible audio tracks still return 415.
- **Behavior regressions**: Browser tests directly capture SDP generated by Chrome, covering portable AAC/MP3, AAC with transcoding capability, direct Opus/G.711, audio-only streams, unknown codecs/capabilities, and notice cleanup; feed tests verify that video-only offers create no transcoding job and continue sending RTP. Both new assertions were observed failing before their respective fixes.
- **Final verification**: Portable and tagged builds, the portable focused tests above, Console/WebRTC tagged race checks, the full tagged race/coverage suite with `LIVEFORGE_REQUIRE_BROWSER=1` and the current build supplied through `LF_BINARY`, lint, and agent-doc checks passed. After the actual 8090 instance was updated to a tagged build, continuous FFmpeg H.264+AAC decoded at 640x360 in WebRTC, with video frames increasing from 661 to 1003 and audio packets from 1051 to 1685; the HLS clock advanced from 24.03 to 50.16 seconds and DASH from 25.68 to 66.14 seconds, both at `readyState=4`. The test publisher was stopped and the service remained running. This result is a bounded local playback verification, not a statement about all input formats or deployment environments.
- **Documentation impact check**: The manifest, full AI navigation, English and Chinese READMEs, and RTMP playback recipe were synchronized; REST, configuration, ports, and top-level discovery entry points did not change, so OpenAPI, the configuration schema, and `llms.txt` needed no additional changes.

### WEBRTC-001: Console WHEP Playback Reports `No advancing media received`

- **Severity**: P0, user-visible, with status `Default Console and SIP/GB28181 Protocol Lab paths fixed and accepted in real browsers`.
- **Symptom**: Console displays `No advancing media received (check codec support and keyframes)` after 8 seconds, and the user cannot see video.
- **Confirmed data flow**: Default WHEP requests in Console and the Protocol Lab now use `mode=live`; explicit `mode=realtime` still creates a reader from `startup.LiveCursor` and discards all non-keyframe video until `gotKeyframe` becomes true.
- **Confirmed failure point**: If `LiveCursor` is after the most recent keyframe and the next input IDR is far away, the input stops sending IDRs, or the input does not respond to PLI, the feed loop keeps reading and discarding video, and the browser receives no decodable first video access unit within the watchdog window. `mode=live` sends the snapshot GOP first, so it can serve as a control.
- **Second failure point (fixed)**: `video.WriteSample`/`audio.WriteSample` errors in `whep_feed.go` now enter WHEP feed status and structured logs; each real transition includes generation, cursor, mode, previous/next states, and a bounded error, without duplicate logging for per-frame updates in the same state. `GET /webrtc/session/{sessionId}/status` exposes first-media time, fixed wait milliseconds, and bounded diagnostics.
- **Test evidence**: Current Pion WHEP H.264 RTP, GCC, AAC->Opus, H.264+PCMA, and VP8 headless Chrome tests pass. The default Console/lab path switched to `mode=live`; explicit `mode=realtime` remains in `waiting_keyframe` until a subsequent IDR arrives. The status endpoint has coverage for generation/cursor/error reads. A new real H.264 Annex-B fixture -> AVCC -> WHEP -> Chromium regression verifies a decoded size of 320x180, ICE connected, no media error, and continuously advancing currentTime when the browser offer advertises H.264; Chromium environments without H.264 receive capability explicitly skip rather than classify the server's correct 415 as a product failure. Independent-port acceptance testing on 2026-08-28 further confirmed that H.264 generated by SIP and GB28181 fake devices both produced 160x90, `readyState=4`, no media error, and continuously advancing `currentTime` in Console WHEP.
- **Remaining verification**: Regressions distinguishing explicit `mode=realtime`, sparse keyframes, and no GOP cache are retained; the 60-second unified matrix soak on 2026-08-30 passed, but longer duration, backpressure, and concurrency capacity still require separate runs and cannot be replaced by the correctness matrix.
- **Acceptance criteria**: Default Console WHEP must receive a decodable video frame and advance `currentTime` within 8 seconds. It may wait for a keyframe before the first frame, but normal GOP intervals must not trigger a misleading failure first, and it must neither silently drop packets nor wait forever. If explicit realtime mode cannot obtain a keyframe promptly, it must display distinguishable waiting/no-keyframe states; on failure, server logs must identify whether the cause is no keyframe, a codec mismatch, or a sample-write error.

## Design Record After Removing `audioCache`

There is currently no separate `audioCache`. A video stream's GOP cache starts with a video keyframe and stores audio arriving interleaved within that GOP; audio-only streams neither wait for keyframes nor depend on GOP cache, and subscribers read the latest audio from the ring buffer's live cursor.

This change alone does not eliminate the lock contention, ring buffer boundaries, transcode reader lifecycles, protocol RTP allocations, configuration refreshes, high-cardinality metrics, or WebRTC first-frame gating issues above. It only removes the duplicate state and incorrect audio-keyframe assumption introduced by separate audio caching; the associated risks must continue to be verified independently.
